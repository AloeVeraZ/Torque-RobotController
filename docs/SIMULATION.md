# Simulation view

Open the **Simulate** tab for offline route planning and driving practice. Entering simulation disconnects live robot controls. Simulation never uploads code or drives a real robot.

The workflow is **Setup → Path planning → Run & review**; each stage tab's number ring shows whether it is done or needs attention, with the reason as its tooltip. Each saved setup owns its field, robot, mechanisms, robot controller and sensing, plus its obstacles, route pins, model references, program and practice timing, so Path planning and Run & review belong to the setup too. The setup picker lists every setup with its field, robot, mechanisms, controller and route; right-click one to open, clone (a "<name> copy" you can then edit), rename or delete it. Opening another setup goes to Setup's **1 · Field**; a setup you left half done (Setup not finished: Path planning never opened) opens on the step you were on, with the box or list you last used in view and focused. Each setup has one field, BIOBUZZ or an empty field (switching changes the field in place); a separate plan is a cloned setup. The preset robots (Starter Mecanum, A301 Swerve) are built-in setups that cannot be deleted or renamed: each opens on its demo route, optimized in the simulator, ready to run, and is cloned to change it. Importing a new CAD or choosing a preset robot for a setup already set up asks first: make a new setup (or open the preset's own), change this setup, or cancel; a custom robot replaced by a preset is kept, and Custom robot brings it back. Preset robot only shows the presets until one is chosen. A preset hides the Setup steps it does not need: Mechanisms on every preset, and Robot controller too except on the Starter Mecanum, which teams build and wire themselves. The Setup step tabs turn amber or red when something on them needs a look (the robot's mass, wheel size or RPM a CAD has none of; a red value; more motors than the game allows), and a line under them says what, with a button to it. The Expansion Hub is ticked on or off (one at most in competition); its address comes from the robot when you set up from the Control Hub. Every change saves automatically on this computer, and Path planning and Run & review show the name of the setup you are editing at the top of the side panel (click it to return to Setup).

## Setup

Setup runs in four steps, like Path planning: **1 · Field** (BIOBUZZ, this season's game, or an empty field; for BIOBUZZ also the alliance). BIOBUZZ is point-symmetric about the field centre (the red GARDEN bottom-left matches the blue one top-right, F1 matches F3), so switching the alliance also moves the starting pose, paths and obstacles to that side, turned 180° about the centre: headings turn by 180°, targets and curve handles move with the field, relative turns, spins and the hive cell stay as they are. Switching back restores them. `deck-sim alliance <setup> blue` does the same (`--keep` leaves the route where it is), **2 · Robot** (Preset robot or Custom robot first; a custom robot has **Import CAD…** on its model's heading, then its size, drivetrain and motors), **3 · Mechanisms** and **4 · Robot controller** (its sensors; what runs the robot is picked in the **Setup** tab). Nothing here asks what is plugged in where: a robot simulates and plans paths with no electronics set up, and those only matter once the real robot is configured in **Setup**. A value the simulation cannot use (an empty box, a 0 lb robot, two devices on one hub port) is red and holds every later step, Path planning and Run until it is fixed; amber only asks you to check. BIOBUZZ keeps FTC's official playing area inside the perimeter wall and cannot be resized; last season's DECODE is no longer offered, and saved DECODE layouts open as empty fields with their zones and pins.

**Preset robots** show only their cards: Starter Mecanum and A301 Swerve are set up and locked (Customize this robot turns one into a custom robot). The Starter Mecanum is the exception, as the goBILDA Strafer-style kit many teams own: its size, weight, wheel RPM, wheel diameter, default autonomous power and driving style can be set to match, and in Robot controller its ports and how the hub is mounted. It runs on a Control Hub with its built-in IMU and the drive motors' own encoders.

**3 · Mechanisms** is on every field. Picking up and shooting pieces (the intakes' and shooters' game physics) belongs to BIOBUZZ; on an empty field every mechanism moves to its named positions when a route action names it.

**Test setup.** A new install opens the **Test setup**: BIOBUZZ red, an FTC Control Hub with a goBILDA Pinpoint, and a robot Deck builds from FTC parts (goBILDA U-channel and mecanum wheels, Yellow Jacket motors, a REV Control Hub, a ramp intake with rollers, and a turret shooter with flywheel, hood and kicker), attached like a CAD import with its joints, wiring and a long red autonomous. Its model is generated, not stored in the app, so it comes back if the models folder is cleared, and `deck-sim show examples/test-setup.json` opens it too.

FTC Control Hub defaults to drive encoders + IMU. Alternatives are two or three tracking pods + IMU, goBILDA Pinpoint, SparkFun OTOS and IMU only. MotionModule supports IMU only, pods and OTOS. Each choice is described in plain words. With **IMU only** there is no position sensing: the robot drives each path for a set time, and **Timed driving** turns distances into times. Its numbers (speed forward and sideways at full power, speed-up and coasting time) are worked out from the robot settings in step 3 (drivetrain, motors, wheels, weight) by driving the simulated robot, so there is nothing to measure; **Use numbers measured on my real robot instead** shows fields for your own measurements and the heading correction strength. It cannot recover a position error. With pods or OTOS, those settings are replaced by **Path correction**: one strength that scales the follower's position feedback and is saved into the exported robot code (0 turns correction off). The simulated sensors always use the typical error of the chosen sensor; there are no separate accuracy inputs, and sensor error never changes the exported gains.

**Sensors** are a list you add to: the IMU (always there; built-in, external, or the Pinpoint/OTOS one), one position sensor (2 odometry pods, 3 odometry pods, goBILDA Pinpoint + 2 pods, or SparkFun OTOS; adding another switches to it), and drive motor encoders. The list sets the sensing the simulator runs and the exports set up. With the Control Hub's built-in IMU, **Control Hub logo faces** and **Its USB ports face** say how the hub sits on the robot. OnBot Java, TeamCode and the Pedro starter constants for odometry pods pass it to the IMU (`RevHubOrientationOnRobot`); a wrong mounting makes every heading wrong. A USB direction along the logo's axis is not possible and is greyed out. From the terminal: `deck-sim robot red.json --hub-logo left --hub-usb up`.

**Where the odometry sits** (with pods, a Pinpoint or an OTOS on a Control Hub) says where each one is on the robot, in inches from its centre (negative is right of it or behind it), and which way it counts:

- **goBILDA Pinpoint**, in goBILDA's own terms: the X (forward) pod's inches left of centre, the Y (strafe) pod's inches forward of it, the pod type (4-bar or swingarm) and whether each pod counts backwards.
- **SparkFun OTOS**: where its chip sits, which way its X arrow points (degrees counterclockwise from the robot's front, SparkFun's offset heading: -90° when its Y arrow points forward, 0° when its X arrow does), and its distance and turn scalars (0.872 to 1.127).
- **Odometry pods**: each forward pod's inches left of centre (the right one's inches right of it), the sideways pod's inches forward, and whether each counts backwards.

The exports set the hardware up with them: `setOffsets`, `setEncoderResolution` and `setEncoderDirections` for the Pinpoint, `setOffset`, `setLinearScalar` and `setAngularScalar` for the OTOS, and a sign per pod. Pedro's starter constants use them too. The virtual Control Hub mounts its pods, Pinpoint and OTOS where these settings say, so in the simulator they are always right; on a real robot, the guided check measures them. Only what differs from Deck's defaults is saved. From the terminal: `deck-sim robot red.json --odometry pinpoint.xOffset=-2.5,pinpoint.pods=swingarm,pinpoint.yReversed=on`.

### Control Hub wiring

**Setup** (its own tab) picks the robot control system, **FTC · Control Hub** or **Other robot**, saved with the setup and used by every tab. An FTC robot can only be given parts the Control Hub's Configure Robot lists allow. The saved-setup bar is only in Simulate.

Connect over USB-C or Wi-Fi and Setup checks the connection, reads the robot's configurations and offers Edit, Activate, Delete and New on them. It asks the robot what is connected, as Configure Robot's Scan does on a Driver Hub, and shows how many **Expansion Hubs**, **Servo Hubs** and other USB devices answered, with each hub's address. Over USB-C nobody has to press **Scan**: it runs when the hub is plugged in and again when a camera, a USB network device or an Expansion Hub comes or goes. Over Wi-Fi the button asks. None of this can be edited in Setup. **Configure** edits a configuration port by port on each hub, and sets how many **Servo Power Modules** there are (a hub servo port boosted to 6 V, which a robot cannot report). A competition robot may have one Expansion Hub (R701); more work on the bench, with a warning.

Setup, Configure and Calibrate follow the cable as it happens. Pull the USB-C and **Your Control Hub dropped** shows at once, whatever Torque was doing, and everything read from the hub goes with it. Plug it in and **Control Hub plugged in** shows before anything has been read, then it moves on by itself: allowed by this computer, Android still starting, reading, scanning. Plugging it back in closes the dropped message. A Driver Hub is ignored from the moment it is plugged in, and a Control Hub in update mode says so. How: Windows tells Torque first (`src/usb-watch/UsbWatch.cs`, a tiny helper that waits on Windows and uses no CPU until something changes, rebuilt with `tools/build-usb-watch.cjs`), and its USB ids and name say what the device is; then ADB's own `track-devices` says what state the hub is in, and only then does Torque read it (`src/usb-watch.cjs`). No ADB runs on a timer while this works, and it rests on every other tab. Where the helper cannot run, ADB's `track-devices` and the old look every 3 seconds take over. `usb-watch.log` in Torque's data folder keeps the time of each event, for reading real latencies.

What is plugged into the Control Hub's own USB ports follows the same way, over USB-C only. While ADB can talk to the hub, one `adb shell` stays open with a small loop on the hub that looks at its USB and network folders twice a second and speaks only when they change, at under 1% of one core with nothing started on each look; each change is read at once and comes to the page on the same event (`src/hub-usb.cjs`). `ui/ftc/usb-kinds.js` says what each device is. That shell ends when the hub leaves or the watch rests, and closes itself on the hub if the computer's end goes away. A scan follows only when what the robot's Scan can see has changed, one at a time, never on Drive, and one that fails tries again without a word. A Limelight has not yet been plugged in to test the part that asks it what it is.

Each device line says what it is, where it is plugged in and what reads it. Two devices on one port are red in Setup, and never hold the simulation or path planning. In **Simulate**, the Chassis card asks only which port each motor or servo is on (and a swerve module's absolute encoder); models come from Setup & Calibrate.

**2 · CAD** is one screen: Import CAD and Remove model, the model and which side is which, then the chassis hitbox (length, width, height and mass) above your robot's parts. Only the parts list scrolls. Wheel RPM, wheel diameter, default auto chassis motor power and the driving style are on the Chassis card in **3 · Mechanisms**. The mass slider spans 0.5–100 lb; positive typed values may exceed convenience slider ranges. Collision planning uses the typed footprint, independently of visual CAD. For a robot imported from CAD, the hitbox is the chassis length × width, filled in on import (from the assembly named Chassis, or every part except the intakes when none is named); intakes still take pieces past its edge but do not enlarge it. The CAD preview sits beside these settings so you can see what each number changes. A reference Yellow Jacket motor model derives geared torque and mass/traction-limited acceleration. Legacy current entries remain for compatibility and are no longer an editable torque multiplier. Electrical references and formulas are recorded in `UNIFIED_PLANNING_CHANGES.md`.

Drop your robot’s CAD on the CAD step (or press **Import CAD…**) and the robot switches to Custom with everything it names filled in. The robot is saved with its setup: **Save file…** in the setup bar keeps the whole setup in one file (field and routes, robot and CAD, mechanisms and robot controller), and **Open file…** opens one. A robot file saved by an older version (Save robot to file) opens with **Open file…** too, into the current setup. Or **start from** a **Preset robot** (DSIM's BIOBUZZ presets: StarterBot, Pollinator, Forager, Skimmer, Sniper, each with its drivetrain, size, motors and mechanisms set; the Pollinator's Box Tube is not simulated) or **Custom**. From your CAD the size is taken from it (from a part named Chassis, or the whole model), with intakes and shooters from named assemblies; adjust any of it afterwards. The red outline in the model preview and on the field is the chassis size; intakes are outlined separately.

Default auto chassis motor power is a ceiling from 0 to 1. Paths inherit it unless overridden; zero stays stopped. Direction comes from route geometry. Sensor noise, scale error and gyro drift are seeded error models fixed by the chosen sensor. Path correction is always on and has no setting: position error becomes a correction speed that is proportional near the path and square-root beyond it (so large errors brake in time instead of overshooting), and when the motors saturate the robot gives up path speed before correction. Gains come from the robot's measured speed, acceleration, weight and size, and the same controller runs in the simulation and the export. Drivetrain families include mecanum, swerve, tank/differential/tracks and omni approximations, identified in the UI.

Empty fields have editable dimensions; BIOBUZZ uses its bundled physics layout. Loose pieces can move and be pushed; with mechanisms set up the robot also picks them up and launches them (below). STEP assemblies merge into one visual body; GLB/STL/OBJ are also supported. Imported geometry is visual only and scales to the typed dimensions. View cubes support face/edge/corner views, pointer-locked drag orbit and Home. Setup JSON files transfer one setup; opening adds it to the saved setups. Virtual keyboard behavior is controlled in the three-dot menu.

## Mechanisms

**Setup → 3 · Mechanisms** is one list of everything on the robot that moves, laid out like DSIM's robot builder: cards you add and remove (×).

- **+ Add mechanism** opens every kind of mechanism, grouped and searchable (claw, lift, extendo, turret, hang…): intakes and claws, pieces moving inside, lifts and slides, arms and linkages, shooters and scoring, hanging, drivetrain and odometry, cameras, robot arms and legs, and your own. It covers every FTC season (Ring It Up's and RES-Q's collectors and climber dumpers, Velocity Vortex's beacon pushers and cap ball forks, Relic Recovery's jewel knocker and relic arm, Rover Ruckus's marker dropper and lander latch, Skystone's foundation grabbers and capstone, Ultimate Goal's ring hopper and wobble arm, Freight Frenzy's duck spinner, PowerPlay's pole guide and cone righter, CENTERSTAGE's purple pixel dropper and drone launcher, INTO THE DEEP's extendo, specimen claw and sample sweeper, DECODE's spindexer and sorter flap), FRC and robots in general. On BIOBUZZ its first group is the game's own: an intake (sweeper roller, side rollers, deployable ramp or kicker) or a shooter (turret or fixed), and a roller intake, drop-down intake, flywheel or turret picked elsewhere is the game's own too.
- **Each mechanism's card** names it (route actions use the name: "Lift up", "Claw open"), says what it is, whether your CAD has it, and its **named positions** both as the part moves (degrees or inches from where the CAD has it) and as the robot code sends them: a servo's position (0–1, `Servo.setPosition`) or a motor's encoder count (`RUN_TO_POSITION`). Type either one.
- **Actuator** on each card says what drives it: a **servo** (to set positions), a **continuous servo**, a **DC motor with encoder** or a **linear servo**, each as the FTC part it is (goBILDA 2000 Torque, Speed, Super Speed and 5-turn servos; Axon MAX, MINI and MICRO; REV Smart Robot Servo; Studica Multi-Mode; goBILDA 5203 Yellow Jacket motors from 6000 to 30 rpm; REV HD Hex with UltraPlanetary or spur gearboxes; REV Core Hex; TorqueNADO; Studica Maverick; older NeveRest; Actuonix L16-R and Hitec HLS12 linear servos), or another robot's (brushless, stepper, pneumatic). Each mechanism type starts with the one teams usually use (a lift a 435 rpm goBILDA on a 1.4 in spool, a claw a goBILDA Speed servo). Its name in the robot configuration and its direction are set here. A servo has its **lowest** and **highest** positions, the position **where your CAD has it** (its center), how far it turns across its rated pulses (300° for goBILDA, 350° for Axon, 270° for REV) and the pulses the hub sends for 0 and 1: FTC's default 600–2400 µs turns a 300° servo 270° from 0 to 1; 500–2500 µs (`setPwmRange`, or Full Range Servo in the configuration) gives all 300°. Its part can only go between its lowest and highest positions. Changing the center keeps the positions you found on the robot. A motor shows its encoder counts per turn and per degree or inch of the part through the gearing after it (**Edit gearing** opens it under Moving parts), its power, and how fast the part moves; the simulator runs it on the motor's torque line. Under the list, the count of motors and servos is checked against FTC's limit (BIOBUZZ R503: 8 motors, the drivetrain's included, and 8 servos); one motor belted to two mechanisms (one name in the configuration) counts once. Over the limit is red on every motor's card, for the team to change the robot; the simulation still runs it.
- **Configure from CAD** says in one line what it set up (intakes, shooters, moving parts, motors and servos, and the Robot controller hardware it saw); **What was found** under it lists every detail. An assembly named only for its piece ("POLLEN V2") is a shooter when it holds a hood or a flywheel (a 6000 rpm motor beside wheels 60 mm or bigger), whatever its feeder wheel's part name says. Each motor and servo in the CAD (goBILDA "6000rpm Motor (GB)", Axon MAX/MINI, SWYFT…) goes to the device that uses it: a fast motor spins a flywheel, the servo under a turret turns it (on both turrets when the CAD lists it once), a shooter with a moving hood gets its hood servo. A goBILDA Pinpoint (or OTOS, or odometry pods) sets the position sensor, an Expansion Hub and REV's Servo Hub (REV-11-1855) are turned on, and other sensors (a break beam, an absolute encoder) are listed with the mechanism they sit in. A mechanism with no motor or servo of its own in the CAD is traced to the one that drives it: its pulleys, sprockets and gears are followed through the belts and chains they touch, the shafts they share and the gears they mesh with (never past a motor, or a wheel's axle beside them) to a motor elsewhere, such as one in the chassis; a motor geared to a mecanum, omni or traction wheel is a drive motor and is passed over. The card then says "Your CAD shows it driven by “Motor Part” in “drivetrain”, through 2 belts or chains", and two mechanisms that reach one motor share it (one name, one port). An Axon MINI on a turret (or swerve steering), which turns past a servo's range through its gears, is set to continuous mode with its feedback wire as the turret's absolute encoder; the exported code then steers it by that wire, counting each wrap of the servo past 0 or 3.3 V, from where the turret is at INIT (its volts per turret degree, in the code, include the gearing).
- **Configure from CAD** finds each mechanism you added in your robot's CAD by the names most like it: its type's words (an extendo in "Horizontal Ext", a lift in "Viper slides"), your own name for it ("Grabby", "Spinny boi"), plurals and one typo; a servo or motor named for it is a piece of it, not it. Each one gets its CAD parts and its pivot, rails or turntable, and its travel when you have not changed its positions; its name, type, actuator and positions stay. On BIOBUZZ the intakes and shooters you added take the CAD's named intake and shooter assemblies: their side, size and spot, keeping their kind, turret or fixed, motors and timing (with none added, the CAD's own are used). The message lists what went where, CAD intakes or shooters you have not added, and the mechanisms nothing in the CAD is named like (name the assembly in your CAD, or **Choose its parts** on the model). The rest of the CAD's moving parts are found with them.

**Hardware** on each card (with the FTC Control Hub) lists every motor and servo the mechanism runs on, each with:

- its **model**, from the full FTC catalog: goBILDA, REV, Axon (with the Axon feedback wire), Studica, SWYFT, continuous and linear servos and every legal motor (a moving part's model is set in its Actuator);
- the **port** it is plugged into, from your configuration in Setup & Calibrate;
- its **sensors**, from those the export can use on that kind of part: the motor's encoder, a REV Through Bore (best on encoder port 0 or 3), an Axon feedback wire, a potentiometer or analog encoder, a limit, magnetic or touch switch, a colour or distance sensor; each with its port and what it tells (where it is, when it is home, how fast it spins, when a piece is there);
- one line on what it is and how the code reads it, such as "Axon MAX "ramp" on Control Hub servo port 0; its feedback wire on analog port 0 tells where intake 1 ramp is."

A flywheel's speed can only come from its motor's encoder, a touch sensor reads only on odd digital channels and a REV potentiometer only on even analog channels: those are red, like two devices on one port. While you click, focus or open a row, or scroll its card to the middle of the page, its CAD parts glow on the model on the right: a turret's motor lights the turret with everything on it, the hood row only the hood. The imported CAD is every part's zero: start the robot posed as in the CAD, and encoders and named positions count from there.

On BIOBUZZ the game's mechanisms are cards in the same list:

- **Intakes** (any number, one motor each): an intake grabs pieces off the floor. Choose its type as option cards (sweeper roller, side rollers, deployable ramp, each saying what it is and what it can reach), the sides it picks up from as chips (front, back, left, right; each side belongs to one intake), and its **size**: how far it sticks out past the frame, how wide its mouth is and how tall its opening is. That box is the intake's hitbox: a piece is taken only when it touches the box's outer face and fits under the opening (pollen 2.8 in, nectar 3.6 in), pieces near the ends of the mouth take a moment longer to funnel in, and the robot cannot drive through the box. The front intake reach that used to be in step 3 is now each intake's size.
- **Kicker** (an intake type): an arm on a servo that swings down in front of the robot, scoops under pieces and swings back up to carry them in. Set how long it takes to swing down and back up, its servo name and the servo positions down and up (0–1; on MotionModule 0–180°). It picks up only once it is all the way down; what it scoops moves on into storage after it is back up, and Shoot waits for that. In a CAD, an assembly named Kicker or Scoop (or one you mark as Kicker in the parts list) becomes one.
- **Deployable ramp** (an intake type): sweeper rollers with a ramp that a servo folds down in front of the robot. The rollers take pieces off the floor whether the ramp is up or down; once it is down it also wedges under a flower's bottom pollen, which a sweeper cannot reach. The ramp moves only on its own **Ramp down** and **Ramp up** steps in the route (Y in teleop, F on the keyboard) and stays where it was sent: **Intake** runs only the rollers, so the ramp no longer drops every time the robot intakes. Set how long it takes to fold down and back up (the game physics' ramp takes 0.3 s), the roller motor, and the servo name and positions down and up. Pieces it takes move straight into storage (no wait, unlike a kicker). Exports drive the servo with `ramp(true)` / `ramp(false)` (`RAMP_1` and so on, `RAMPS` on MotionModule), and robot code that moves the servo moves the ramp in the simulator. A **Kicker** is different: it is the scoop itself, so it still swings down while Intake runs.
- **Shooters** (up to two): a turret (a flywheel on a turntable that points itself at the hive) or a fixed shooter (fires one way; Shoot pins turn that side toward the hive), what it shoots (pollen, nectar, or both, for each shooter) and its position on a 3×3 grid with the front marked. Two shooters on their own turrets cannot share a cell or sit next to each other, which the grid enforces. With two turrets, shooter 2's **Turret** choice puts it **On shooter 1's turret** instead: both flywheels ride one turntable (the center is allowed), one turret motor aims them together, and both launch from that spot. In the exports shooter 2 then has no turret of its own (there is no `TURRET_2`).
- **Shooter timing**: spin-up time; **transfer time**, from a piece touching the intake to sitting in the shooter when the robot is empty (pieces behind it stop sooner: with 4 slots and 2 s, 2, 1.5, 1 then 0.5 s); and **indexing time**, for the next piece to move up into the shooter after a shot. A piece in the shooter fires as soon as the flywheel is at speed and the shooter is on target. Each turret aims from its own spot on the robot. Turret speed and range when there is a turret. The game physics allows 13 shots a second, so these times set the pace.
- **Preloads**, at the bottom: pollen and nectar limits (like the game, storage holds 4 pieces in any mix; nectar needs a shooter that takes it) and the pollen the robot starts with (BIOBUZZ preloads are pollen).

**From your CAD.** Robot description files bring their joints with them, confirmed (**From the file** in Moving parts), and are drawn at their true size:

- URDF;
- SDFormat (.sdf, .world, from Gazebo);
- MuJoCo (.xml);
- text USD (.usda, from Isaac Sim; save binary USD as .usda first).

Their meshes are found beside them, as ROS and Gazebo find packages and models. The import says what the file had that is not read.

A big STEP robot is read once: its pieces are read on every core, each with only its own parts' colours, and its facet size is chosen while reading so it never needs a second read (a 152 MB, 903-part robot: about 85 s instead of 190 s on a laptop). The same file again comes from the cache in seconds.

Before a robot file (STEP, GLB, STL, OBJ or one of the above, chosen, dropped or sent from `deck-sim`) is read, the app asks whether it is the robot's starting position; the robot is simulated exactly as the CAD is posed, so export it with slides down and mechanisms stowed as it sits before a match. **No, cancel** imports nothing. A STEP assembly whose assemblies are named sets the robot up on import: **Chassis** (or Drivetrain, Frame, Base) sets the chassis length and width and is what the model is fitted to; anything named **Intake** (or Roller, Sweeper, Ramp) becomes an intake on the side it sticks out of, with its reach, mouth width and height from its size; **Shooter**, **Launcher**, **Flywheel** or **Turret** becomes a shooter at its spot (a turret when the name says turret; pollen or nectar when the name says so); **Indexer**, **Feeder**, **Transfer** or **Hopper** is noted so you set its times. The import message lists what it found. Changing which side is the front (or top) carries the chassis size with the CAD, and every intake or shooter tied to it (from a named part, or placed by clicking the model) stays on that part with its kind, motors, power and timing kept. Sides picked with the buttons are the robot's own and stay. **Configure from CAD** on the Mechanisms page places the intakes and shooters you added from the part names again. A **URDF** (.urdf) imports with its joints: each link is drawn where it sits with every joint at zero, mesh files it names are read (STL, OBJ or glTF; `package://` paths are found in the folders above the URDF, as ROS finds packages; a Collada .dae is listed as not drawn and its link's collision shapes stand in), and its revolute, continuous, prismatic, fixed, floating and planar joints, limits and mimic tags become moving parts marked **From the file**. The terminal does the same: `deck-sim robot <setup> --cad robot.step --front +x --top +z`.

On the 2D field the robot is a top-down picture of its model (bundled or yours), the red dashed outline is the chassis, each intake box is dashed in the intake colour and each shooter is a dashed circle in its piece colour (yellow pollen, red nectar, orange both). The 3D view shows the model itself, its moving parts moving (see **Moving parts** below). A very detailed CAD (more than 400,000 triangles) is drawn there and in run videos as a lighter copy, with screws, fillets and threads merged, so the view stays smooth; the Robot and Mechanisms previews keep every detail for picking parts.

Each part has a collapsed **Robot hardware** section that says what the exported code drives, so it matches how the robot is built:

- **Intake rollers:** a DC motor or a continuous servo, an optional second roller (side rollers usually have two), the power, and **Turns the other way** for a roller mounted to run backwards. Kickers and ramps have their servo and its positions down and up.
- **Flywheel:** its motor, an optional second motor (two-motor flywheels), and which way each turns.
- **Feeder:** a motor or continuous servo that runs while shooting (with its direction), a **servo pusher** that swings to its push position for each shot and back to rest while the next piece drops in, or a **servo gate** that opens while shooting. Servo feeders have their two positions.
- **Turret:** the motor or servo name and its direction.

Under Shooter timing, **Flywheel and turret on the robot** sets how the flywheels hold their speed: velocity control with an encoder (speed in RPM, encoder ticks per revolution, how close counts as at speed, and an optional velocity PIDF), or a set power when there is no encoder (it counts as at speed after the spin-up time). It also sets what the turret turns on: a motor with an encoder (ticks per degree; it counts from where it is at INIT, so start the robot with each turret facing forward) or a servo (its position facing forward, and the turret's degrees across the servo's range). A servo pusher's push time is there too. The terminal sets the same hardware: `deck-sim mech <setup> --intake-device crservo --flywheel-second shooter_b --flywheel-second-reversed on --indexer pusher --feed-pos 0.7 --rest-pos 0.2 --turret-kind servo --pidf 1.26,0.126,0,12.6` (`deck-sim help` lists every flag).

The simulator runs the code with these devices: the virtual Control Hub registers each one as what it is, mounted the way the settings say, so robot code that turns a device the wrong way spits pieces out or does not shoot, as on the robot.

With a robot model (bundled or your imported CAD), the page also shows the model with every part marked; **Place on model** on a part, then a click on the model, sets where that part is (the nearest edge for an intake, the nearest grid cell for a shooter). Which way is the front comes from step 3. The terminal sets the same parts: `deck-sim mech <setup> --intakes front+back:sweeper,left:ramp --shooters turret@center:pollen,fixed@back>back:nectar --pollen 3 --nectar 1 --preload 3`.

### What turns with what

**Configure from CAD** follows each motor through the CAD itself. A pulley or gear on a shaft turns with the shaft, and so does what rides on it: wheels, spacers, and the pieces of a star or tube wheel arranged around it. Pulleys on one belt share its speed, by their teeth. Two round gears whose pitch circles touch turn opposite ways, by their teeth; two whose axes meet at a right angle turn each other too. The drive stops at a differential (a gear between two others on one line, which has two ways to go), at a gear with a bearing in its bore, which spins freely on its shaft, at another motor or servo, and at a shaft two motors reach at different speeds.

Each roller, feeder and flywheel gets its ratio to its motor, and every other shaft on that motor follows it at its own speed: **Show gears and wheels** in Moving parts lists them. When a feeder's motor also turns wheels right behind the intake's rollers, the rollers and the feeder run together, on one motor or two: **Turns together with the intake rollers** on the Feeder's card says so, and the team can change it.

**A model sets the speeds.** A roller or feeder turns at its motor's speed times that ratio, a flywheel up to it, a turret and a hood at the servo's speed through their gears, and a ramp folds in its range at its servo's speed. With no model chosen they use REV's numbers (an HD Hex 20:1 motor, a Smart Robot Servo). Every one of these is a number on that part's card to type over. Speeds are shown as they are up to 300 RPM; above that they grow slowly, so a 6000 RPM flywheel still looks faster than a 3000 RPM one without strobing.

Each model and sensor has its own photo in its list and on hover, from its maker's listing. A model with no listing to show keeps a plain drawing rather than another maker's photo: the REV Smart Robot Servo UltraSpeed, PLEX, TORCTEX PRO and MICRO, and MATA TORQUE.

### What a mechanism asks

Every motor or servo on a mechanism asks the same things in the same order: what it runs on (a DC motor, or a servo that is set position, linear or continuous), its model, what it is plugged into, what powers it, and a sensor or No sensor. Only what it runs on matters to the simulation; the rest is for the real robot and can stay unset. **Configure from CAD** fills in what your CAD shows.

A ramp has one time to fold both ways and a range from 0, where the CAD has it. Type a number and it turns on the model; a negative number turns it the other way and makes that way positive. The feeder is part of the intake. The turret has its own card: a second motor or servo on its gear train, and the gear pairs from there to the turret, read from the CAD's part names where they give the teeth.

### Moving parts

Under the model on the Mechanisms page, **Moving parts** lists what moves on your CAD and how. Only your CAD is drawn: the turret, hood and ramp that move are its own parts. A STEP file from Onshape, SolidWorks or Fusion keeps its assembly names but not its mates, so the first time the page opens with a new CAD the app looks for them itself (a second or two on a 2-million-triangle robot) from the shapes and names of the parts.

Each intake and shooter is matched to its CAD assemblies first. Ones you named in the Robot section (or with **Set up from CAD**) are used as they are; otherwise the app takes the assemblies whose names say what they are (the pollen shooter, the front intake), then by where they sit; and in a CAD with no such names it looks for each shooter's flywheel in the whole body and takes the assembly holding it, and for a ramp's hinge among the parts on its side. The status line says which assembly each one was linked to.

- **Turret:** the large round part with an upright axis under each shooter (a turntable gear, ring or bearing) is its pivot; the shooter's parts and that gear turn on it. Which way it fires in the CAD comes from the flywheel and hood (over the flywheel, away from the hood), shown as an arrow; turn it in 90° steps if it is wrong. In the simulator a turret angle of 0° faces the front, as the exported code assumes at INIT.
- **Flywheel:** the largest round part with a level axle in the shooter, with everything on that axle. It spins at the flywheel speed, drawn slower so it can be seen.
- **Hood (pitch):** parts named Hood, with the spacers and bearings on their shafts. It pivots on the flywheel axle when its arc is centred there (the usual adjustable hood), else on the shaft at its end. When it pivots on the axle, the app works out the angle your CAD launches at (along the hood's end, the way the flywheel carries the piece) and tilts the hood by the difference to the **Launch angle** while the shooter spins up or aims. Before that it turns the hood each way until it meets another part, and keeps it within that range (**Tilts down to / up to**), so it never passes through the turret; when the launch angle is out of reach it stops at its limit and says so. **Set the tilt myself** goes back to resting and shooting angles of your own. Shots leave at the game physics' launch angle either way.
- **Gears:** a gear beside a turret's turntable or a hood's gear rack, whose teeth mesh with it, turns with it the other way by the tooth ratio (from tooth counts in the part names, "Spur gear (20 teeth)" or "100t", else from the gears' sizes), with the parts on its axle; so do the gears that one meshes with, back to the servos (two servos on one pinion included). Servo bodies stay put. Each shows as its own part that follows the one before (under **Linked to other parts**).
- **Ramp or kicker:** the hinge is where hinge hardware lines up along the intake's edge (a servo hub, hub shaft or axle, with the servo's output on it); what swings is what lies beyond the hinge and is not held by the plates that carry it. **Down** is worked out as the angle where it first touches the floor, **Up** is how the CAD has it, and the times to go down and up are the intake's own. **Pickup box from the ramp** sets the intake's green box (where it picks up) to what the ramp's parts reach when down.
  - Every intake is looked through for a hinge, whatever it is set up as or named. A plate that swings down on a servo hub in front of rollers makes the intake a **Deployable ramp**; with no rollers, a **Kicker**.
  - **Configure from CAD** sets the intake to that, as does the first look at a new CAD.
  - Otherwise the ramp says the intake is set up as a sweeper, so it stays up in runs, and offers **Make intake 1 a deployable ramp**.
- **Roller arm:** a roller whose axle sits in plates that turn on another axle (usually the axle that drives it, with its pulley), inside side plates with a slot or cutout round that axle. The slot sets how far it lifts. It rests where your CAD has it and rides up over each piece the intake takes in; the roller spins on it.
- **Rollers and feeder wheels:** round parts on one axle with a roller or wheel among them; they turn while the intake runs or the robot feeds. Star and flex wheels (not round, but centred on the axle with their spokes repeating round it) turn with their axle too, whatever they are named. An axle carrying them is a roller or feeder axle even with no wheel named on it.
- **Drive wheels:** wheels touching the floor roll as the robot drives.
- **Not in your CAD yet:** a turret or ramp the game needs but the app could not find is listed with no parts. The simulator still turns it, but nothing is drawn for it: open it, click **Choose parts** and click its parts on the model (Shift-click takes a whole assembly), then **Pick a circle** on what it turns on.

**Mechanisms found by name.** Any assembly you named for a mechanism, at any depth of your CAD, is found too: claws, wrists, lifts, linear slides (extendos), arms, four-bars and virtual four-bars, buckets, gates, kickers, transfers, spindexers, hang hooks, winches, swerve modules, camera mounts, and robot-arm joints, legs, gantries and pistons, 57 types in all. The last mechanism word in a name decides ("Intake slides" is a slide, "Claw wrist" a wrist); vendor parts ("48mm Gecko Wheel (GB)") and hardware named after a mechanism ("Arm motor mount", "Claw servo", "4BAR HEX") are pieces, not mechanisms, and same-named parts that do not touch (the side plates of a four-bar) are copies, not one part. One inside another rides on it, so **Outtake › Lift › Arm › Claw** becomes a claw on an arm on a lift. Where each one moves comes from its parts: a pivot on the hinge line joining it to what holds it (a servo hub, a pin named for it), a slide along its rails (the stage bolted to the frame stays), a spinning part on its biggest axle, a turntable on its upright round part, a claw's fingers (parts named finger, jaw or pincer) each on its own hinge pin, closing together. The type sets its named positions ("Claw open/closed", "Lift down/up", "Arm down/up"), speed, which way positive turns (arms and hooks raise) and the motor it usually has. A named assembly whose pivot cannot be found is still listed, in the middle of its parts, for you to pick the pivot. While BIOBUZZ's mechanisms are on, its turrets, hoods, flywheels, intakes and feeders stay the ones set up for the game.

**Hitboxes** (at the top of the list, and the 3D view's own Hitboxes button) shows a box round each moving part's CAD parts: the turret, hood, flywheel, ramp and rollers, each in its colour. The boxes move with the parts, in the preview, in runs and in run videos.

Each one says how sure the finder is (**Found · likely right** or **Found · please check**, with a score and the reason), and **Set by you** once changed. Open one to see its pivot (an axis and a ring through the model, over everything) and its parts glowing, and to change it:

- **Pick a circle:** click a round part (gear, bearing, shaft, wheel), a hole or a round edge, and its circle is measured and becomes the pivot, the way a slicer measures one. **Two points** sets the axis through two clicks. **Flip direction** reverses which way positive turns.
- **Choose parts:** click parts to add or remove them (Shift-click takes the part's whole assembly). **Rides on** puts it on another moving part (a hood on its turret).
- **Moves by:** pivot, spin, slide, turn and slide, screw, universal, ball, planar, floating or pin in a slot (the joint types URDF, SDF and MuJoCo use). **Driven by:** the turret, hood, flywheel, rollers, ramp or feeder of a mechanism, the drive wheels, or named positions for route actions.
- **Check clearance** turns the part through its range (the others as the preview has them) and says how far it moves freely and what it first meets each way; **Show it** poses the contact with both parts glowing red, and **Use as limits** keeps it within the free range. It checks boxes around each part, so a contact is worth a look rather than certain, and parts already touching in the CAD (an axle in its bearing) do not count. On the lunala robot, turret 2 meets turret 1's pulley 114° from where the CAD has it.
- **Try it** turns the part on the model; **Show up**, **Show down** and the other buttons pose it at a position. **Play** runs every part through its motion. **Exact pivot** has the pivot and axis in robot inches.
- **Linked to other parts:** **Follows** another part by a ratio (−1 mirrors a gripper finger, a gear pair is minus the tooth ratio, a cascade stage is 1); **Pin it to** another part (or the robot) at a pin you click closes a loop, such as a four-bar, and the parts it moves are worked out to keep it closed.
- **Mechanism:** what the part is, from the same list. Picking another keeps its parts and pivot and takes the new type's motion, positions and speed (a claw made a lift slides 0–24 in). The line under it says what the type is and what usually drives it; **+ Motor** in Motor and gearing then adds that motor as the FTC part it usually is (a goBILDA Speed servo for a claw, a 435 rpm goBILDA motor on a 1.4 in spool for a lift).
- **Find again** looks once more, keeping what you set, and looks for the mechanisms you added that have no parts yet, as Configure from CAD does. New mechanisms are added with **+ Add mechanism** above the list (each with its motor or servo), then found with **Configure from CAD** or placed with **Choose its parts**. A setup whose moving parts were found by an older version is looked at again when the page opens, keeping what you set.

**Motor and gearing** (in a part moved by actions) gives the part its motor:

- **Motor:** servo, DC motor, brushless motor, stepper, linear actuator, pneumatic or hydraulic cylinder.
- **Gearing:** stages from the motor to the part (gearbox ratio, belt or gear teeth, a spool's or pinion's diameter, a lead screw's lead).
- **Moves:**
  - at its set speed;
  - as a DC motor: enter the free speed and stall torque from its datasheet, how many motors, the load it holds (gravity on an arm, for example) and optionally what it moves. The panel shows the part's top speed, stall torque and speed under that load, and in the simulation it slows under the load and cannot lift past stall;
  - as a pneumatic cylinder, which only rests at its ends.

The part keeps its named positions and its route actions ("Lift up").

**Poses** save where several parts are in the preview ("Home", "Over the bin"); a step going to a pose moves every part in it so they all arrive together, as an industrial arm's joint move does. **Sensors** read how the robot actually moves in the simulation, not what it was told:

- an encoder on a motor counts its turns;
- a limit switch closes at a position;
- an angle or distance sensor reads one;
- a speed sensor reads a motor's speed.

**Actions** (under the list) are steps that move parts together, one after another or after a wait ("Score: lift up, then claw open 0.25 s later"). A step can also go to a pose, wait for a sensor (closes, opens, reads at least or at most, giving up after its time), wait a while, or run another action, so an action can be built from others ("Pick and place" from "Grab" and "Release"). **Repeat** runs it several times (a cycle, a gait). **Play** shows one on the model. Path and pin editors offer them, and each part's positions ("Ramp down"), next to the game's actions; at a pin the robot waits until they are done. On fields other than BIOBUZZ, step 3 is **Moving parts** alone: a ramp, kicker, hood or turret found from the part names is moved by these actions, and every mechanism found by name (above) is proposed too, for you to check. An assembly named only "Outtake" is looked inside for its lift, arm and claw rather than taken for a shooter. Mecanum drive wheels roll with sideways motion as well (one diagonal pair forward, the other back).

During runs the engine works out every joint's value each tick (the turret angle, how far a ramp is down, the hood's tilt, each spinning part's angle) and sends them with each frame, so the 3D view, recordings and run videos show the same motion; gears that follow a turret or hood are turned with it as each picture is drawn. On an imported CAD a mechanism with no CAD parts is turned without being drawn; only a bundled chassis gets a plain stand-in shape for it.

Routes use them as **steps**. Every path and every pin has its own list of steps, added with one tap: the game's actions, **Turret angle**, a moving part's positions or **to an angle…** (or **to a length…** for a slide), **Wait**, or **Your own…** by name. At a pin the robot arrives (and turns, if set), **pauses**, then runs its steps **one after another, top to bottom**: each for its set time, or until it is done (leave the seconds empty). For example: Shoot → Ramp down → Intake for 1.5 s → Ramp up. On a path the steps run **together** from the start of the path, each for the **whole path** or a **set time**: Intake + Ramp down, or Spin up + Turret to 30°. ↑ and ↓ reorder steps, × removes one; a list holds up to 8.

| Action | At a pin | While driving a path |
| --- | --- | --- |
| Intake | Runs the intake rollers for the time set (1 s unless changed) | Runs the rollers for the whole path or the time set |
| Ramp down / Ramp up | Folds the ramp and waits until it is there; it stays there | Folds the ramp as the path starts |
| Turret to 30° | Turns the turret (or Turret 1 / Turret 2) to that angle from the robot's front, + left, and waits until it is there | Turns it while driving |
| A part's position or angle | Moves the part (Setup → Moving parts) and waits until it arrives | Moves it while driving |
| Wait | Waits its time before the next step | (nothing) |
| Shoot | Spins up, aims and shoots until the robot is empty, or for the time set | Shoots for the whole path or the time set |
| Spin up | Starts the flywheel and moves on | Starts the flywheel early |
| Aim | Waits until the turret points at the target | Keeps aiming while driving |

**Aim at** (Shoot and Aim): the hive cell up at the start, or the **other cell**. A hive tips once enough pieces land in its up cell (your alliance's start cell holds 3 nectar, so 3 pollen tip it; the other cell then faces up and takes 8), each tip scoring 20; aim later volleys at the other cell. The other cell is reached from the far side of the hive. Terminal: `--cell other` / `--path-cell other`.

Older routes still load: a single action becomes one step, "Shoot 3" shoots three pieces, and an Intake pin's pause becomes its intake time. The path list shows each path and, under it, the **pin** it ends at: the path's row says what runs while driving ("While driving: Intake + Ramp down"), and the pin's row what happens there ("pause 0.5 s → Shoot → Ramp down → drive on"). Click either to edit it in place. The exports run the same order: `WAIT_SECONDS`, then `ACTIONS` for `ACTION_SECONDS` (0: until done), and `MOVING_ACTIONS` for `MOVING_SECONDS` (0: the whole path); an action gets `step.duration` and a last call with `step.last` when its time is up. A pin or path with several steps runs under one name ("Shoot then Ramp down", "Intake + Ramp down"): RouteActions.java's `Steps` (and `STEPS` in MotionModule's autonomous.py) calls each step's own method in turn or together, so every step still has its own slot for your code. In the terminal: `deck-sim pin <setup> add 40 30 --wait 0.5 --action Shoot --for 1`, `--action "Shoot; Ramp down; Intake for 1.5"` for several steps, and `--path-action "Intake; Ramp down" --path-for 0.6` for a path.

In teleop and full-match practice, Controller 1 runs them too: right bumper intakes, left trigger spins up, right trigger shoots, Y folds a ramp down or back up (keyboard: E, Shift, G, F).

The game physics does the rest: pieces are captured only by the sides that have an intake and only while there is room for that piece, launched one at a time along each shooter's actual direction (a turret where it aimed, a fixed shooter along its facing) and scored by BIOBUZZ's rules, so a turret aimed from a poor position estimate misses. Each shooter takes only the pieces it is set to shoot. Shots aim at the selected alliance's hive (its up-facing cell at the start). Any other action name is your own, with an empty code slot in the export.

**Exports run the same mechanisms.** For a Control Hub, OnBot Java, TeamCode and Pedro add `Mechanisms.java` with a field and constants for each device (`INTAKE_1`, `INTAKE_1_REVERSED`, `FLYWHEEL_1`, `FLYWHEEL_1B`, `FEEDER_1`, `TURRET_1` and so on), each device's direction set in `init`. Every method is called once per loop and never waits, so the robot keeps following its path while an action runs:

- `intake(on)` runs the rollers and lowers kickers (raising them again when it stops); `ramp(down)` folds ramps down or up, and they stay there. `turnTurret(shooter, degrees)` and `turnTurrets(degrees)` turn turrets for Turret to steps. Rollers and roller feeders are looked up as `DcMotorSimple`, so a motor or a continuous servo both work there.
- `spin(on)` starts the flywheels with `setVelocity` (`RUN_USING_ENCODER`, with the PIDF when one is set) or a set power.
- `ready()` is true once every flywheel is within the at-speed tolerance, or after the spin-up time plus half a second so a weak battery cannot stall the autonomous (with no encoder: after the spin-up time).
- `aim(pose, cell)` turns each turret from its own spot on the robot. A motor turret uses `RUN_TO_POSITION`. A servo turret is tracked turning at the turret speed and counts as aimed within 2°.
- `shoot(n, step)` spins up and aims, waits until the flywheels are ready, the turrets aimed and the last intake's pieces have had the transfer time, then feeds for n shots: `(n - 1) x FEED_CYCLE_SECONDS + LAST_SHOT_SECONDS`. A pusher pushes once per cycle.

The built-in actions call it. To do one your own way, override that action in `RobotActions` (the generated file shows how); the others keep working. Every Control Hub export also has a **check TeleOp** (`<Class>Check.java`, named "<route> check (Deck)"): a guided check of every device, one step at a time, before the autonomous runs. With the robot on blocks, each step turns one device or moves one servo and asks on the Driver Station:

- **The IMU**: whether it reads the robot level, and whether a quarter turn left reads as a left turn. A wrong reading means the Control Hub mounting in Deck is wrong.
- **Each drive wheel** turns at low power: did it turn so the robot would drive forward?
- **Each intake roller**, each **flywheel motor** and each motor or continuous-servo **feeder** turns on its own: did it pull pieces in, spin the way that shoots, move pieces toward the flywheel? A flywheel motor answered "the other way" is flipped at once, so the next step measures the flywheels' **top speed** at full power with every motor helping, for REV's velocity PIDF (F = 32767 ÷ top speed, P = 0.1 F, I = 0.1 P, D = 0).
- **Each servo** (kicker and ramp down and up, pusher and gate rest and feed) starts at its setting. The D-pad moves it, a little (up and down) or more (right and left), until A saves where it is. B keeps the setting.
- **A motor turret** turns a little: did it turn left? Then it is pointed straight ahead and a quarter turn left with the D-pad, which measures its encoder ticks per degree. **A servo turret** is pointed the same way, which finds its center, its range and its direction.
- **The odometry** comes last, with the robot on the floor. Push it straight forward by hand, exactly 48 in (two tiles) if you can measure it, then about 24 in to its left. The counts say which way each pod counts, or whether the OTOS's axes are turned or mirrored. The 48 in push also gives the Pinpoint's pod type or the OTOS's distance scalar; X ("another distance") finds the directions only. Then the robot turns once on the spot under its own power. How each reading changes with the turn gives where each pod or the OTOS sits, and the OTOS's turn against the hub IMU's gives its turn scalar. A wheel found turning the wrong way earlier in the check is already turned the right way for this.

Answer on gamepad 1: A yes, B no (the other way), X nothing moved, Y again. Telemetry's **Deck results** line lists every answer as the Deck setting it means, for example `v1 robot.frontRight.reversed=true intakes.0.downPos=0.150 shooter.pidf=2.3405,0.2341,0,23.4050`. Run from Send to robot's **Guided check**, Deck shows each question with buttons for the answers and puts the results into the setup. After the last step, right bumper, left trigger and right trigger try the intake, flywheels and feeders with the settings in the code.

For MotionModule, `autonomous.py` gets a `Mechanisms` class on its motor and servo outputs, looked up by hardware.py name or else on free channels: the drive uses motors 1-4, so mechanisms take motors 5-8 (motor intake rollers, then each shooter's motor feeder and flywheel motors), positional servos (kickers, ramps, servo feeders, turrets) start at 0 and continuous servos (rollers and feeders) at 6. A device that turns the other way runs with its power negated. A robot needing more than four mechanism motors says so in the code. MotionModule motors have no encoders and no X/Y sensing, so its flywheels are timed and a servo turret (about ±90°) aims from the planned pose. Only the export for the selected controller is shown. The virtual Control Hub and MotionModule's own runtime run these exports against the same physics (`deck-sim test --code onbot|teamcode|motionmodule`).

## Run data

Run & review → **Results** is where a run is reported. Before the first run it says what Run will do in this practice mode and shows Path planning's test-drive time; when the planned route cannot run yet it says **Fix the route before running it**, with the route check's message and **Fix path N**. Run opens Results (unless a Java program is being edited under Export), and a report that arrives while another view is open marks the Results tab. When a route run ends, the **Run report** is built only from the recorded frames: a verdict (finished cleanly, finished with things to check, or ran out of autonomous time); the route time against the autonomous period; how far the robot stopped from the last end point; **Position tracking**, how far the robot's own sensor estimate was off at the end (the label's tooltip says what that means); contact with the field wall, field structures or no-go zones that began after the robot left its start pose (starting against the wall is normal), each tied to the path where it happened; and points. Under the facts is the next step: **Fix path N** when something went wrong, otherwise **Export to your robot**, and **See each step** (Diagnostics → Run output). **Where the time went** is drawn on the autonomous period's scale: start-up, one segment per path split into driving, turning in place, stopped for an action or pause (intaking, spinning up, shooting) and stopped with nothing running, then the time left as spare, with seconds marked under the bar. One path is chosen (the longest, until you click another): its breakdown shows under the bar with **Edit path N**, and the field marks that path. Clicking a path also replays its start. **What to try next** lists up to three suggestions taken from those numbers, with **Edit path N** buttons that open that path in Path planning, or **Open Optimize** / **Open Space around obstacles**, which open that setting under Path planning → Route options. The report is labelled as a simulated estimate.

The **Summary** under the graphs lists the time recorded, pieces picked up, pieces shot, how many landed in the hive (and the accuracy), hive tips, points, pieces still held and zone touches. `deck-sim test` prints the same numbers.

In Path planning, once edits settle the planned route is test-driven in the background with the same physics and follower as Run (about a second), and the status line above the planning tabs shows **about N s in simulation**, flagged when it is longer than the autonomous period or the test drive touched something or missed the end point. Click the status line (**Details**) to open the route checks under it: every issue, with an **Edit path N** link, plus warnings such as zero motor power. Click it again to close them.

Run & review → **Results** → **Replay the run** records every frame of a run and graphs it: speed, heading, sensor estimate error and drive power are shown by default, with turn rate, X/Y position, flywheel, turret, pieces held and points under **Choose graphs** (values a run did not record are left out). Each graph shows the value at the selected time and its range over the run. Drag the **timeline** or any graph to replay the field and views together (green is autonomous, blue teleop; **Live** follows the robot again). Under **Robot at this moment** (folded), the **mechanism view** shows the intake, stored pieces, turret angle and flywheel speed at the selected time, and the **wheel view** shows wheel motion, with swerve modules pointing where the physics steers them.

**Compare with a robot log** (folded under Run & review → **Results**; it works before any run) opens a log from the real robot and draws where it actually drove in orange beside the planned route. It lists how far the robot strayed from the plan (on average and at the worst point, which is circled and named by its path) and how far from the last end point it stopped. Supported logs:

- WPILOG with a Pose2d entry, such as AdvantageKit's `/RealOutputs/Odometry/Robot`, in the FTC field frame AdvantageScope uses. Deck's own run logs read back exactly.
- CSV with `x`, `y` and optional `heading` and `time` columns. Names such as `pose_x` or `Robot X (in)` work too, and so do spreadsheet exports: a byte-order mark, quoted cells, and decimal commas when `;` separates the columns. Units come from the header (`x_in`, `x_m`, `heading_deg`, `heading_rad`); without them the values are taken as inches, and headings that all fit within ±2π as radians. Coordinates are measured either from the bottom-left corner (Deck, Pedro Pathing) or from the field centre (FTC SDK).

Only logged positions are used. A log without poses is refused, and nothing is filled in.

Run & review → **Export** → **Save this run: log or video** → **Save run log (.wpilog)…** saves the last run as a WPILOG (AdvantageKit key layout: robot pose at `/RealOutputs/Odometry/Robot` plus the estimate, BIOBUZZ pieces as Pollen and Nectar positions, drive and mechanism values, and the DriverStation enabled/autonomous/alliance state), for sharing or for comparing with logs from the real robot in a log viewer. From the terminal: `deck-sim test --log run.wpilog`.

### Run videos

## Shared field editing

One field remains visible beside Starting pose, Field obstacles and Paths. Field obstacles is a step only on an empty field: BIOBUZZ brings its own structures, so a game field goes from Starting pose straight to Paths. Drag existing obstacles, points or the robot from any submenu. Select is the default obstacle tool.

**Paths** works like the Pedro Pathing visualizer. The list starts with the starting pose, then one row per path; each path drives from the previous point to its end point. Click the field or **+ Add path** to add one, or **Draw path** to turn a stroke into paths. Clicking a row, its line or its point opens it in place: end X/Y, heading (constant, linear to a field heading, turn by an angle, face a target, back to the start heading or spin), shape, motor power and its steps while driving. Under each path is the pin it ends at, with its own row: its pause, a turn there, and its steps in order. **Shape → Custom curve (drag handles)** works like Pedro Pathing's visualizer: the path becomes a Bezier curve with two control points, shown as round handles joined to the path's ends by dashed guides. They start where the current shape already is (the planned curve's own control points, or a third and two thirds along a straight path), so nothing jumps; drag them to bend the path, or type exact positions in the path card’s **Handle 1/2 X/Y** boxes (they follow the handles while you drag). Hold Shift while dragging to snap a handle to a 0.5 in grid. The right-click path editor offers the same shapes and headings as the path card. The robot then drives exactly that curve: the planner checks the whole robot footprint along it, with the path's heading setting, and if it would touch a wall, structure or no-go zone the path is marked as an issue (its curve drawn dashed red) instead of being re-routed. Undo keeps the path open with its handles. Optimize leaves custom curves alone, every export uses the same control points (Deck Java and OnBot Java, Pedro `Paths.curve`, `.pp` control points), and tank-style robots, which drive straight legs, do not offer it. In the terminal a path's `controls` array holds 1–3 points (`deck-sim pins` reads and keeps them). **Path options…** and **Pin options…** open the full editors (heading, turns at the pin, notes); right-click still opens them from the field. Axis and number labels cannot become text selections while dragging.

**Zoom and pan (2D).** Scroll over the field (or pinch on a trackpad) to zoom in up to 8× around the pointer; **−**, **Fit** and **+** beside 2D/3D do the same (in 3D they give way to **Hitboxes**), as do the - = and 0 keys when the field has focus. On a touchscreen, pinch with two fingers. To move around a zoomed field, drag any empty part of the floor (in Run & review, drag anywhere); a press that does not move is still a click, so Click to add still adds a path. The middle mouse button and Space+drag pan too. While zoomed in, a small map of the whole field in the top-right corner outlines the part in view: click or drag it to jump elsewhere without zooming out. It shows while you zoom or pan and fades 2 s after you stop, so it does not cover the route; it stays while the left button is held on the field or the map, or while the pointer is over it. Everything still works zoomed in: dragging pins, curve handles, obstacles and the robot, and clicking to add paths.

**Paths** has two views: **Paths** (the list) and **Route options** (route shape, turning, space around obstacles, Optimize, importing a .pp file and clearing paths). The **?** beside **+ Add path** opens the editing help and the keys over the list.

**Keys** (the **?** lists them): arrows nudge the selected end point or obstacle 1 in (Shift: 0.1 in), Delete removes it (or the open path), Enter edits it, [ and ] turn an obstacle by 15°, Escape cancels, Ctrl+Z and Ctrl+Shift+Z undo and redo, and scroll, + − and 0 zoom. Each path row has **⧉ Duplicate**, which inserts a copy with the same settings right after it, ending at a clear spot 12 in along. The copy's curve handles are not kept, because they belonged to the original's start.

While a path is open, faint robot outlines every 8 in along it show where the whole footprint goes, at the heading it has there (like the Pedro visualizer's onion layers).

**Preview.** Under the path list, drag the scrubber (or press **▶ Preview**) to move a robot outline along the whole planned route, turning on the spot where the plan turns. It shows the shape only, at about 30 in per second, with no physics; Run & review drives the route with physics and timing. The note beside it names the path and the inches driven so far, and that path's card is marked in the list.

Mouse robot dragging locks the pointer and constrains the footprint against barriers, with sliding and no hidden pointer travel buildup. Touch follows the finger. Start at edge finds a clear boundary pose. Box, circle, triangle and custom-shape tools create physical barriers. Custom outlines are normalized; disconnected pieces remain separate.

Double-click an obstacle to edit its dimensions/angle/corners. Double-click a pin for its pause, steps, heading and note. Click a path for its power, shape, steps while driving, heading and note. Hover a path for its modifiers and endpoint headings; color/styling identifies modifiers.

Each popup edits an isolated draft. Clicking outside or pressing Escape leaves it open. **Done** validates and saves that object; another editor cannot open until Done. Drag the header/grip to reposition it. Pick target on field keeps the popup visible while accepting the next field click. Escape cancels target picking.

Live diagnostics check every pin and path after pose, obstacle, footprint and route changes. They distinguish clearance failures, heading sweeps, target singularities, sensor warnings and timing cautions. Obstacles affect physics and route geometry.

## Shapes, headings and power

The global route shape is Smooth curves or Straight lines. Each path may inherit or override it. Old rounded-corner files still load; that redundant UI choice migrates to straight. Unsafe splines tighten or fall back to safe straight/detour geometry.

Optimize test-drives mixed straight/spline assignments through physics, keeping the fastest tested route that touches no zone and finishes within 1.5 inches of the final pin. Up to four unlocked paths are searched exhaustively; longer routes use bounded patterns and individual flips around the winner. Explicit path choices stay fixed. Optimizer-owned choices may be reconsidered. This is a measured candidate search, not proof of a global minimum.

Per-path motor power overrides the setup default. Heading modifiers include inherited heading, relative rotation, absolute heading, spin and tracking a field point. **Face along the path** (Pedro Pathing’s tangent heading) keeps the robot’s front pointing the way it is driving at every point of the curve, and **Face backwards along the path** does the same with its back. The robot first turns in place to face along the path where it starts (and at any corner of an automatic detour), the turning footprint is checked along the whole curve, and the next path keeps the heading it ends with. Exports use Pedro’s `.tangent()`/`.reverseTangent()`, the same interpolator in Deck Java and OnBot Java, and `tangential` in `.pp` files; timed (IMU-only) and MotionModule exports turn steadily from the start tangent to the end tangent instead. Relative turns accumulate: after +90°, an unmodified path keeps that orientation; -90° returns it. Target bearing uses the exact curve position, and its final heading carries into the next unmodified path. Pins can turn before the next path. Tank routes stop and turn between straight legs; all turns and pauses consume autonomous time.

## FTC OnBot Java export

For supported FTC mecanum and tank/differential/tracked robots with positional sensing, **OnBot Java (.java)** exports one public LinearOpMode containing the complete Deck controller, route geometry/headings, motor powers, turns/waits, hardware/localization adapter, the mechanisms and the action slots, and beside it the check TeleOp (`<Class>Check.java`, which uses the autonomous file's `Mechanisms`). Imports are only FTC SDK and Java standard library. No external pathing library, deck.sim package or Android Studio project is needed.

Upload both files through Control Hub OnBot Java, Build Everything, then select the autonomous on the Driver Station and INIT/START (or let **Send to robot** below do the uploading and building). See the [official FIRST tutorial](https://ftc-docs.firstinspires.org/en/latest/programming_resources/onbot_java/OnBot-Java-Tutorial.html). Match hardware names, motor directions, IMU mounting, wheel travel and sensor offsets to the actual robot: the drive motor and sensor names (and drive motors that turn the other way) are under **Setup → Robot controller → Device names on the robot**, and the mechanism devices under each part's **Robot hardware**. Generated gains are starting values requiring real calibration. Intake, Spin up, Aim, Shoot, Ramp down/up and Turret to N° run the mechanisms set up in Deck (`Mechanisms.java`, with the hood servo set for Spin up and Shoot), and the moving parts' actions such as "Lift up" or "Arm to 30" run them in `Parts.java`, the same names the simulator runs. A part or ramp with a position sensor (an Axon's feedback wire, a potentiometer) is done once the sensor says it is there, and otherwise after the time the simulator gives the move; a motor once RUN_TO_POSITION is done. Every hub reads its inputs in one go per loop (bulk caching). Anything else, or your own version of one of those, goes in RobotActions. Writing TeamCode over an old RobotActions.java takes out its untouched empty methods for actions Deck now runs (a `.bak` copy stays beside it), so they no longer override Deck's code. **Robot configuration (.xml)…** saves the Control Hub configuration as Setup wires it. The virtual hub completes placeholder actions immediately; configured pauses supply their simulated duration.

### Send to robot

Run & review → Export → **Send to robot** puts the autonomous on a Control Hub over its Wi-Fi, with no Android Studio and no OnBot Java editor. Join the robot's Wi-Fi first and pick the robot: the FTC robots saved in Settings, a Control Hub at 192.168.43.1 or a Robot Controller phone at 192.168.49.1. Opening Export with a robot saved in Settings checks its configuration against Setup once a session.

1. **Check robot** reads the robot's active configuration as a Driver Station does (`CMD_REQUEST_CONFIGURATIONS`, then `CMD_REQUEST_PARTICULAR_CONFIGURATION` for its XML) and checks every device name the export uses, the sensors, hood and moving parts included. For each name it says whether the robot has it as the right kind of device (a motor, a servo, a continuous servo, an IMU, a Pinpoint, an OTOS or a sensor), with its hub and port, and whether that is the port and motor type Setup gives it. Rollers and roller feeders accept a motor or a continuous servo.
2. A name the robot lacks gets a list of the robot's devices of the right kind, with the one that plainly means the same device already chosen (its `leftFront` for Deck's `front_left`, `Intake` for `intake`), or **Add it to the robot**. **Use these names** saves the choices into the setup, so the code uses the robot's own names. A device the robot has as another kind says which Deck setting to change (for example a turret configured as a servo).
3. **Send to robot…** checks again. Devices left to add go on the port Setup's wiring gives them; the rest get ports: Deck scans the robot's hubs (`CMD_SCAN`, `CMD_DISCOVER_LYNX_MODULES`) and plans drive motors on the Control Hub, other motors on the Expansion Hub first, and servos and sensors on the Control Hub first (sensors from I2C bus 1). A list shows the port for each, with a motor type for each motor. Pick the port a device is already plugged into, and the two planned devices swap. A robot with no active configuration gets one with every hub its scan found. Then Deck lists what it will do: the names, the configuration, the upload.
4. **Save and send** (or **Upload and build** when nothing is added) saves the names into the setup. It saves the configuration as a new one ("competition Deck", a copy of the active "competition" with the devices added; "Deck <setup>" for a robot that had none) with `CMD_SAVE_CONFIGURATION`, makes it active, reads it back and restarts the robot. A configuration the robot already has is never replaced. Then it uploads the autonomous and the check TeleOp with the robot's OnBot Java server (`POST /java/file/save` on port 8080) and builds them (`/java/build/start`, `/java/build/status`). A file the robot already has with other contents (someone edited it in OnBot Java) is copied to this computer first, under the app's data folder in `robot-backups`; OnBot Java also keeps its own copy of the source on every build. Compiler errors are listed with their file and line. The devices to plug in stay listed with their ports, and the next time this robot is opened in Drive (within the hour) the autonomous is selected.
5. **Guided check** runs the check TeleOp from the panel once the robot has it built: **Start the guided check…**, then each step's question with a button for each answer (Controller 1's A, B, X, Y and D-pad answer too). **STOP**, or Space, stops it. The settings the answers change are listed as they come in; **Use these settings and send…** stops the check, saves them into the setup and runs Send to robot again, leaving its **Upload and build** to press.

Send to robot never starts the autonomous. Close the robot in Drive first: one Driver Station at a time can talk to the robot, and leaving the Simulation view stops a running check. The protocol comes from FTC SDK 12.0's own classes, and the app is tested against a simulated Control Hub that answers the same way (`node tools/ftc-sim.cjs 127.0.0.2 --onbot`, with `--empty` for a robot with no configuration), not against a real one.

### Pedro Pathing 3 export

For mecanum and swerve robots with position sensing, **Pedro Pathing 3…** writes TeamCode (swerve robots get no starter constants, and Deck's Follower runs only cover mecanum) for a project built from the [Pedro Pathing Quickstart](https://github.com/Pedro-Pathing/Quickstart) (`com.pedropathing:revhub:3.0.2` on FTC SDK 12.0.0, as the Quickstart pins them). It writes `<Class>Paths.java` (the starting pose and one `Path` method per leg, plus the per-leg tables), `<Class>Pedro.java` (the `@Autonomous` LinearOpMode), `RouteActions.java`, `RobotActions.java` (created once, then kept), `<Class>Check.java` (the check TeleOp) and, with mechanisms, `Mechanisms.java`. The OpMode gets its Follower from the Quickstart's `pedro/Constants.java` (`Constants.create(hardwareMap)`); until you fill that in it returns null, and the OpMode then says so on the Driver Station and does not move.

- Coordinates are copied as they are: Pedro uses the planner's frame (inches, origin bottom-left, +X right, +Y up, heading counterclockwise).
- Lines and curves become `Paths.line`/`Paths.curve` with the planner's control points. A constant heading is `.constant(...)`, a turn on a straight line under half a revolution is Pedro's `.linear(...)`, tracking a target is `.facingPoint(...)`. Longer turns, spins and turns on curves use `Interpolator.geometric` with the planned turn, because Pedro's `linear` takes the short way round and spreads the turn by distance, which would differ from the headings the planner checked for clearance.
- Per-path motor power becomes Foresight's `maxPathSpeed` for that path only (`path.with(config.maxPathSpeed.at(...))`): a fraction of the robot's top speed rather than a motor power cap. A zero-power path stops the robot until the end of autonomous.
- The OpMode runs the legs once, in order: turn in place if the next leg starts at a new heading (done when within 1.5° for 0.15 s, at most 5 s; Pedro's own hold timeout is too short for this), follow the leg while running its action-path action, settle, turn after if asked, pause, then run the end-of-leg action. Legs that only split for a power or action-path change are driven straight through. Every loop checks `opModeIsActive()`, Stop during INIT moves nothing, and the drive (`follower.stop()` plus `drivetrain.stop()`) and mechanisms stop in `finally`.
- The export panel lists what is checked (compilation, path geometry) and what is the team's (Pedro setup and tuning, starting pose, action code, a real test on the field).

For a mecanum robot with goBILDA Pinpoint, SparkFun OTOS, or two or three odometry pods with the hub IMU, the export also writes `pedro/DeckStarterConstants.java` beside the Quickstart's `Constants.java`. It builds the Follower from Pedro's own REV hub `Mecanum` drivetrain and `PinpointLocalizer`, `OTOSLocalizer`, `TwoWheelLocalizer` or `ThreeWheelIMULocalizer` (pod names, offsets, directions and ticks per inch, the Pinpoint's pod type, and the OTOS's offset and scalars, all from **Where the odometry sits**), with the motor names and directions from Deck and a Foresight config filled from the simulated robot. That config uses the same quantities Pedro's Foresight tuner measures: top speeds, natural deceleration, braking coefficients, and heading and translational gains. They are estimates of the robot you described, not measurements of your robot. To use them while you tune, return `DeckStarterConstants.create(h)` from `Constants.create`, then replace the numbers with what the Quickstart tuners measure. Run the guided check first, so the odometry offsets and directions are your robot's. Deck's OTOS offset uses SparkFun's frame (X forward); the starter constants turn it into the one Pedro's `OTOSLocalizer` expects.

**Run with Pedro's real Follower.** `node tools/simulation/fetch-pedro.cjs` downloads Pedro Pathing core and revhub 3.0.2 from Maven Central into `.cache/pedro/3.0.2`, checking their SHA-1. After that, `deck-sim test <setup> --code pedro` runs the Pedro export on the virtual Control Hub with Pedro's own Follower, built by `DeckStarterConstants`, against the simulator's FTC SDK stand-ins and physics. `tests/sim-pedro-runtime.test.cjs` does the same for these cases (pod localizers measure velocity with the wall clock, so those runs are paced in real time):

- a pause and a turning path;
- OTOS sensing;
- Stop part-way along a path;
- a zero-power path;
- the BIOBUZZ example with its mechanisms.

The packaged app does not include Pedro. This is a development check.

Tank-style robots are not offered: Pedro 3's REV hub module has mecanum and swerve drivetrains. `deck-sim export <setup> --format pedro --out TeamCode/src/main/java/` writes the same files.

Control Hub TeamCode exports the same implementation as separate package files and preserves existing RobotActions.java. Route Java exports geometry for the bundled Deck API and is not a standalone FTC program. The path file (`.pp`) opens in the current [Pedro Pathing visualizer](https://visualizer.pedropathing.com/), and **Import path file (.pp)…** (Paths, beside Clear all paths; `deck-sim import-pp <setup> <file.pp>`) brings one back. It replaces the starting pose and paths, and one Ctrl+Z undoes it.

- **A file Deck exported, unedited:** opens exactly as saved. It carries Deck's pins and zones and a fingerprint of its lines.
- **A Pedro Visualizer file, or one edited there:** each line becomes a pin and its path. Control points become a custom curve (Deck keeps up to 3). The heading becomes the path's turning (tangential, constant, linear, facing a point, or a long turn). Waits before, after and in the sequence become pauses and actions at the end points. A group's single turn is split across its segments.
- **Anything Deck can only approximate** is listed after importing.
- **On a game field,** the Visualizer's shapes are left out, because Deck's field already has the structures. The Visualizer keeps only its own fields when it saves, so Deck-only settings (motor power, action paths, turns at the end point) do not survive editing there.

The path file On a game field its coordinates are measured from the inside of the perimeter wall, as the Visualizer's 141.5 in field is: Deck keeps the wall inside a 144 in square, so a BIOBUZZ `.pp` is shifted by the wall (1.33 in) and records the shift as `deckOrigin`. Empty fields are not shifted. The file also sets the Visualizer's robot size (`settings.rWidth`/`rHeight`) to Deck's collision footprint, so its robot outline and onion layers match. The Pedro Pathing Java export keeps Deck's own coordinates. They match Pedro's documented frame (the FTC field-centre frame plus 72 in, so the wall is about 1.3 in from the origin), and the OpMode sets its starting pose itself. Each line is an atomic path with its control points and a heading object (constant, linear, tangential, or a facing-point piecewise heading for tracking a target). The Visualizer turns a linear heading the short way and spreads it by arc length, so a turn of 179° or more, a spin, or a turn along a curve is written as piecewise linear pieces of at most 120° each, placed where the robot reaches each angle. Loaded into the Visualizer's own code, every heading type stays within 0.6° of what the robot drives. the start has `headingDeg`, pauses and the action after them are `waitAfterMs`/`waitAfterName`, and no-go zones are shapes. Deck's own fields (motor power, action paths, turns at pins) stay alongside for other readers; the visualizer turns linear headings the short way round. MotionModule has its own timed Python exporter and virtual runtime check. Unsupported hardware adapters and IMU-only FTC setups do not claim a complete positional FTC export.

## Terminal (deck-sim)

Everything in Path planning and Run & review can also be driven from a terminal, so a person or an AI assistant can build and test a route quickly and then see it in the app. Run `deck-sim help` from the repository folder (`deck-sim.cmd` on Windows uses Node.js, or the app's own runtime when Node.js is not installed; elsewhere use `node tools/deck-sim.cjs`).

```
deck-sim field biobuzz                     # hive cells, flowers, gardens, loading zones, start rules
deck-sim new red.json --field biobuzz --length 17 --width 17 --sensors fused --power 1
deck-sim robot red.json --cad robot.step   # or .stl/.obj/.glb; sizes the collision footprint
deck-sim start red.json 9.83 27 0
deck-sim alliance red.json red
deck-sim mech red.json --shooter turret --spin-up 0.8 --index-seconds 0.35   # mechanisms (deck-sim help lists every option)
deck-sim pin red.json add 38 28 --path-action Launch --power 0.6 --track 59.25,58.56 --wait 0.4
deck-sim pins red.json pins.json           # or replace every pin from a JSON array
deck-sim plan red.json                     # blocked pins are listed like Diagnostics
deck-sim test red.json                     # same physics and follower as Run
deck-sim test red.json --code onbot        # runs the exported OnBot Java on the virtual Control Hub
deck-sim test mm.json --code motionmodule  # runs the exported autonomous.py on MotionModule's runtime
deck-sim optimize red.json                 # fastest safe spline/straight shape per path
deck-sim compare red.json robot.wpilog     # a real robot's log against the plan (CSV too; --origin center for FTC frame)
deck-sim export red.json --format onbot --out TeamCode/
deck-sim show red.json --run               # opens it in the app on Run & review and starts it
```

`show`, and `--show` on any command that changes a setup, launches the installed app, or hands the setup to the window that is already open. The setup opens as a new saved setup, the route is planned and the requested tab (`--tab run`, `plan` or `setup`) is shown. A robot CAD file named with `robot --cad` is imported as the robot model. Opening Simulation closes any live robot connection, as it does from the Simulate tab. `--dev` uses this checkout's Electron runtime instead of the installed app. Add `--json` to `field`, `plan`, `test`, `compare` and `info` for machine-readable output.

## Calibrate

Calibrate measures the real robot so the simulation and the code you send match it: Live debug reads every port while you drive outputs, and each mechanism walks gated steps (identify, direction, units, zero, range, feedforward, feedback, sensor thresholds, commit) chosen by what measures it. The shooter's calibrated hood angle by flywheel speed and speed lost per shot run in the simulation (the hood joint follows the flywheel's speed). See [CALIBRATION.md](CALIBRATION.md).

## Controller, physics and development

Coordinates are inches from bottom-left, +X right, +Y up, headings counterclockwise from +X. The Deck controller samples exact Bezier geometry by arc length, ramps reference speed, applies velocity feedforward, position feedback and heading PD, and caps combined wheel commands to motor power. It consumes sensor estimates, never truth. Native timing uses an injected simulation clock; FTC uses ElapsedTime.

DSIM advances at 60 Hz with reference-motor dynamics, traction, contact and braking. Empty fields are planar; BIOBUZZ uses Rapier 3D. Truth and sensor estimates are displayed separately. Poor calibration or sensor errors may still cause an execution miss. Bounded stall recovery can back out along recent motion; it does not plan around unknown real obstacles.

The virtual Control Hub compiles the exported OpMode, Deck controller and adapter against project-authored SDK stand-ins, running in lockstep with physics. The actual FTC SDK is not bundled. Motor directions, encoder signs, braking, pods, Pinpoint, OTOS and IMU readings feed the generated adapter. The Pinpoint and OTOS work as the chips do: mounted where the setup says, they turn their pods' counts or optical motion into a pose with what the code configured (offsets, directions, pod type, scalars). Code configured differently is off the way a real robot would be.

Build with `node tools/simulation/build.cjs`; fetch pinned dependencies with `tools/simulation/fetch.cjs`. DSIM is the upstream simulator source dependency. The own controller is `tools/simulation/java/deck/pathing/DeckFollower.java`; its exact source is embedded in `ui/sim-follower-source.js` for exports. Generated runtime files are under `sim-runtime/driver/`, `occt/` and `java/`; the Java bridge is `deck.sim.RunBridge`. The renderer uses a planning worker and a separate simulation utility process. Stop invalidates pending replies and stops Java. CAD import runs off the UI thread.

Run `node --test --test-concurrency=2 tests/*.test.cjs`. `node tools/simulation/check-ftc-sdk.cjs` temporarily downloads checksum-verified FTC SDK 12.0 RobotCore/Hardware and Pedro Pathing 3.0.2 core/revhub references, compiles the OnBot Java, TeamCode and Pedro exports as Java 8 for sensor/turn/action/tank cases and for every setup in `examples/` (so the generated mechanism code is compiled too), checks stand-in member signatures and deletes the references. These checks do not establish physical robot calibration or performance.

Public packages omit field/chassis CAD whose terms forbid redistribution. Personal local builds may preserve existing assets. DSIM is PolyForm Noncommercial. Historical drivetrain-adapter BSD attribution and all dependency notices remain in `THIRD-PARTY-NOTICES.md` and bundled licenses.
